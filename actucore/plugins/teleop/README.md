# PICO 遥操卡片

`teleop` 是普通 ActuCore 内的一张卡片。Canvas 用于连接管理、参数配置、会话操作和执行状态查看；PICO 提供双手柄输入、透视画面及就地操作按钮。日常遥操不需要运行后端脚本，也不需要点击 Canvas 的整个项目“运行”。

当前天轶双臂已完成实体 PICO 跟随、松握把保持、恢复与结束收臂的现场验证。该结果不表示灵巧手、其他机型或长期稳定性均已验收。北京 G1 的部署展示与真实运动验收应分别记录，不能继承天轶结果。

## 先找到卡片

1. 打开机器人 PhanthyMotus 页面，进入 Canvas。
2. 在侧栏 **执行（ActuCore）** 中找到 `teleop`，拖到画布。如果已经有遥操卡片，直接使用原卡片；当前只支持一个实例。
3. 卡片展开后可看到运行模式、会话状态、硬件执行状态，以及当前机型支持的操作。天轶包括“开始遥操 / 暂停保持 / 恢复遥操 / 结束并收臂 / 立即停止”；G1 不显示尚未实现的收臂操作。
4. 当前遥操通过服务配置选定 Driver，不需要给卡片连一条机械臂指令线。输出端口是状态 JSON，供观察使用。

侧栏没有 `teleop` 时，表示当前 ActuCore 未启用插件，或镜像没有提供该能力。添加一张普通参数卡不能替代服务部署。卡片存在但没有中文面板时，检查 Agent Core 是否支持 `x-connection-panel: teleop-v1`。

## 配置服务

在会话结束、控制权释放后，展开 **服务配置**。保存需要当前项目停止且具备 Canvas 编辑权；保存配置不会开始运动。

| 配置 | 含义 |
|---|---|
| 运行模式 | `shadow` 只计算和显示；`live` 才允许申请 Driver 执行权 |
| 机器人机型 | 天轶为 `tianyi2`；原厂每臂 5 关节的 G1 为 `g1_23` |
| 位姿映射 | 天轶使用 `relative_v1`；G1 还提供 PR #152 的头部朝向映射及相对握持映射 |
| 位移比例 | `relative_v1` 可设置 0.01～1；G1 的两个 PR #152 映射要求为 1 |
| 模拟反馈来源 | 默认 `teleop_executor`；`driver_joints` 只用于 G1 Shadow 读取普通 Driver 的关节数据 |
| 机器人命名空间 | 必须与所选 Driver 的本机 ROS topic 一致 |
| Driver MCP 地址 | 本机 Driver 的 `/mcp` 地址，必须为显式回环 IP |
| 标定文件路径 | 容器内已经部署的标定文件；这里不是上传文件入口 |

点击 **保存并应用配置**，等待服务确认，再检查读回值。随后在 **诊断与维护** 点击 **重新标定**。当前速度、手掌变换与碰撞几何仍来自标定文件，卡片不提供这些文件的编辑器。TLS、配对状态目录和管理密钥由部署配置提供，不在日常表单中填写。

已接受的参数会保存在 Core，并在 ActuCore 配对状态目录旁保存一份重启恢复缓存。重启恢复参数，不恢复动作、会话或控制权。诊断区的快捷模式切换也会更新 ActuCore 配置；需要明确与 Core 的保存值同步时，使用完整的“保存并应用配置”表单。

## 首次配对与后续连接

1. Canvas 展开 **连接与配对**，点击 **允许新设备配对**。
2. 在 PICO 打开“连接机器人”，选择目标机器人并申请配对。
3. 对照头显和 Canvas 显示的指纹；一致后，在卡片点击 **指纹一致，批准**。
4. PICO 进入已配对机器人的透视采集页。卡片应显示“已连接”；佩戴并进入采集页后，再检查头显与左右手柄跟踪状态。

已配对设备以后可以在 PICO 直接选择机器人，不需要每次使用电脑批准，也不需要 USB。配对只是建立信任，不会开始遥操。**断开头显**保留配对；**撤销配对**后需要重新申请。

## 从 Canvas 开始一次遥操

1. 正确佩戴 PICO，左右手柄分别持于身体两侧，打开透视采集页，松开双握把和扳机。
2. 在卡片 **诊断与维护 → 重新标定**，确认显示“已加载”。这一步加载已部署的机器人模型和标定配置，不会移动机器人，也不等于重新测量模型尺寸。
3. 核对模式。点击 **开始遥操**，等待“等待双握把”。Canvas 的当前开始入口要求已经标定；天轶 PICO 的开始按钮会先执行零输出标定，两个入口暂未完全统一。
4. 同时按住左右手柄侧面的握把键，移动手柄。只有 Live 且 Driver 反馈“硬件正在执行”时，才表示正在下发真实动作；Shadow 的模型运动不会驱动机器人。
5. 松开任意握把，双臂保持。再次握住时，从当前手柄和实测双臂姿态建立新的相对基准。
6. 结束时按下表选择操作，观察实际结果。

| 操作 | 结果 |
|---|---|
| 暂停保持 | 暂停输入并请求保持；保留会话供恢复 |
| 恢复遥操 | 显式恢复或重新准备会话，之后重新满足双握把条件 |
| 结束并收臂 | 当前仅支持天轶双臂模式；先停止遥操输入，再缓慢返回当前原厂模型的双臂零位，确认后释放控制权 |
| 立即停止 | 请求停止并释放控制权，不主动收臂；网络失败或停止未确认时，页面会保留未知或错误状态 |

“结束并收臂”要求当前配对头显仍在线，即使从 Canvas 发起也是如此。界面显示请求已接收，不等于已经收臂完成。断线、碰撞或反馈异常会中止收臂并报告原因；原因解除后可以显式重试。收臂不是任意障碍环境中的自动规划路径。

天轶 PICO 的三个按钮与卡片用途相同：用任一手柄射线指向按钮、扣一下扳机。开始要求松开双握把；结束与停止可用于中止当前输入。G1 目前没有接入这套头显操作按钮，不应据此判断其配对失败。

## 如何看状态与头显模型

卡片区分三件事：PICO 是否在线、会话是否正在处理输入、Driver 是否实际输出。反馈过期时显示“执行状态未知”，不能用“已连接”或“遥操中”代替真实执行反馈。

天轶头显中的显示含义：

- 绿色线：新鲜关节实测值计算的双臂位置。
- 黄／橙色线：完整 IK 结果；它不是已经执行到位的证明。
- 粉色目标：相对映射后的末端目标。
- 带 `HELD` 标记的橙色模型：最后有效解的历史快照，不是当前有效指令。
- 白色躯干参考：辨认朝向；外框表示标定的活动边界，框内并非所有姿态都可达。

越界或短暂 IK 失败时，失败目标不下发，保持靠近最后有效执行位置。天轶在保持已确认、输入和反馈恢复有效后可继续，不做额外的越界目标搜索。普通松握把后重握会重新建立相对基准；真正故障的恢复仍需满足 Driver 条件。

G1 与天轶的模型点数、历史显示及恢复实现有差异，不能将天轶显示和恢复验收直接套用到 G1。

## 机型支持边界

| 能力 | 天轶 2.0 | G1_23 |
|---|---|---|
| 双臂 IK | 每臂 7 关节 | 每臂 5 关节 |
| 配对、RTC 输入、Canvas 管理 | 已实现 | 已实现 |
| PICO 内开始／结束／停止按钮 | 已实现 | 尚未接入 |
| 结束并收臂 | 已实现，仅已标定双臂模式 | 尚未实现；不声明或显示此操作 |
| 手部 | 支持标定开合区间，但当前现场验收关闭手部 | 固定假手，不输出手部命令 |
| 普通 Driver 只读 Shadow | 不提供此适配 | 支持 `driver_joints`，没有执行权 |
| 录制管理入口 | 10 秒 Shadow 录制 | 尚未接入 |

北京 G1 的卡片展示可以先使用 Shadow；IK 仍需要带 `pinocchio.casadi` 的 G1 数值环境，不能直接复用天轶依赖锁。若要真实运动，还需要其配套执行 Driver、模型／碰撞标定和独立验收；仅修改 `robot_profile` 不足以完成适配。

## 部署与接口

生产结构是一套 ActuCore：VLA 与 `teleop` 共用进程、ROS executor 和 MCP **15730**。PICO WSS **15741** 是插件内部的输入与显示服务，不是第二个 ActuCore。旧独立 `actucore-teleop` 与 15740 现场布局不再作为新部署方案。

JetPack 6.1 可使用仓库构建入口 `deploy/build_actucore.sh --jp-version 6.1 --with-teleop`。该发布脚本在配置远端仓库凭据时会推送镜像；仅本地构建须使用项目约定的 Dockerfile 构建方式。构建、挂载和配置恢复约束见 [ActuCore README](../../README.md#遥操与-vla-共用-actucore)。共享依赖锁是 `requirements.bundle.lock`；CPU 隔离验证镜像不构成另一套生产服务。

将 [配置示例](config.example.yaml) 的 `plugins.teleop` 合入现有配置，保留其他插件。新部署还必须提供标定、TLS、配对状态、管理密钥与 DDS 文件的挂载；标准 service 片段尚未自动生成全部遥操挂载，不能只打开 `enabled` 就宣称部署完成。`/deploy/dds-local.xml` 必须和宿主挂载的 DDS profile 一致。Core 的 `TELEOP_MANAGEMENT_URL` 指向共享的本机 15730 MCP，管理凭据只由 Core／ActuCore 持有。

低频 MCP 操作包括 `info/config/start/pause/resume/finish/stop`、配对、标定、自检及录制。连续目标通过本机 ROS domain 42 的 `/{namespace}/motion/teleop/command` 发送，反馈为同前缀的 `/feedback`，状态为 `/{namespace}/teleop/status`。Driver 独立负责控制权、时效、机械边界及停止反馈。

天轶录制入口 `record_start/record_stop/record_status` 仅在 Shadow 且无租约时使用。`record_start` 等待有效双握把输入后录制 10 秒，记录输入、反馈和版本信息，不录入配对凭据；当前 Canvas 未提供录制按钮。离线分析和回放接口位于 [acceptance.py](acceptance.py)，真实回放必须与纯分析区分。

## 验证与开发资料

本地检查示例（仓库根目录，使用已准备的依赖环境）：

```bash
python -m pytest agent-core/tests/test_teleop_panel_metadata.py -q
python -m pytest actucore/tests/test_operator_session.py actucore/tests/test_teleop_configuration_restart.py -q
node agent-core/tests/teleop-panel.browser.cjs
```

浏览器检查使用本地 fixture；`test_tianyi_execution_chain.py` 需要将 `TIANYI_DRIVER_SOURCE` 指向配套 Driver 源码。内存替身、隔离 ROS、镜像启动及实机动作是不同证据等级，不能相互替代。跟随误差与延迟如实报告，不另设精度通过门槛。

架构边界与后续问题见 [遥操架构说明](../../../docs/design/teleop-architecture.md)。现场证据和一次性迁移记录单独保存，不构成通用安装流程。模型与客户端来源、许可证见 [NOTICE.md](NOTICE.md) 和 [ADOPTED_SOURCE.json](ADOPTED_SOURCE.json)。
