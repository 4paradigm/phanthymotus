# Canvas 与 PICO 遥操生命周期

## 目标与边界

用户在 Canvas 拖入 teleop 和对应 Driver，连接控制端口、配对 PICO、开启智能控制，然后从 PICO 开始遥操。PICO 结束遥操或 Canvas 结束智能控制都应停止输入、将天轶双臂回到原厂零位的自然下垂姿态、确认后释放控制权。此处“原位”沿用已经采用的自然下垂零位，不改为本次接管时的任意姿态。

本轮仅离线开发与验证，不连接、部署或驱动天轶和北京 G1。Core 主 PR 统一为 #259，#261 已关闭；Driver 配套 PR 为 #321。G1 尚无收臂操作，不将天轶生命周期冒充为 G1 验收。

## 实现

1. Driver 用 `control/teleop` 输入和 `x-teleop-target` 声明实际命令/反馈 topic、命名空间、机型及协议版本。Canvas 根据保存的唯一控制连线和当前 MCP 注册地址生成绑定，拒绝缺失、多目标和不兼容绑定。
2. 开启智能控制调用 `project_start`，只保留内存中的 armed 权限，不创建运动会话、控制租约或目标；重启不恢复权限。PICO/卡片的开始和恢复共用入口，必须 armed，按实际反馈标定后等待双握把。
3. PICO 结束与 Canvas 项目停止复用同一收臂实现。项目停止先禁用新开始，再撤销输入，等待已有操作，完成收臂与控制权释放后才停止其他卡片。项目停止不依赖头显在线。
4. 失败保留实际错误和可重试状态，不把“收到请求”当作收臂完成，不继续启动其他动作。立即停止仍为取消收臂并停止，不主动回零。重复结束/停止不得重复运动。
5. Canvas 显示连接目标、待开始、收臂中、停止失败和重试；PICO 显示尚未开启智能控制，禁止提前开始。日常使用不需要后端脚本配置 endpoint。

## 验证

- 实际 Core 图解析和生命周期入口：唯一绑定、开启零运动、停止顺序、错误保留及重试、旧接口和图修改不能绕过停止。
- 实际 ActuCore 运行时、操作队列和 Driver 执行状态机：开始、输入、松握/重握、两种正常结束、头显断开后项目停止、并发开始/停止、重复结束、重启权限不恢复。
- 使用有速度约束与跟随滞后的离线关节反馈；保留目标、实际反馈、收敛与停止凭证，区分模拟执行与物理验收。
- 原生客户端解析/按钮测试、Canvas 浏览器测试及相关回归；只在变化或失败需要时扩大验证。

## 交付

代码、使用说明和验证记录同仓提交到既有 PR；不创建新 PR。部署和实体 PICO/天轶验收待用户明确设备可用后再进行。

## 离线结果（2026-09-22）

上述实现已完成。Core 在其他卡片真正就绪后才允许 PICO 开始；关闭智能控制等待收臂完成凭证，失败保留原图与反馈通路。停止中修改图、替换方案和旧启停接口均不能跳过这条流程。G1 保留原独立 Shadow 卡片操作，但明确拒绝尚未支持的项目收臂生命周期。

测试发现并修复：已经释放的旧租约导致收臂重试失败；立即停止清除准备状态后无法再主动收臂；旧异步回执覆盖更新的停止结果；准备 RPC 返回期间项目停止仍创建输入会话；新收臂 Event 覆盖立即停止取消信号。
